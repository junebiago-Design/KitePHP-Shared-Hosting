# JS ↔ PHP Framework for InfinityFree

A reusable request bridge you can drop into any new client project. Built
around the two InfinityFree quirks that actually break naive `fetch()` +
`php://input` code in production:

1. **Manually setting `Content-Type: application/json` in JS gets flagged by
   the WAF.** Fix: never set it. Send `FormData` instead — the browser sets
   its own multipart boundary, which the firewall ignores.
2. **Background GET requests can be blocked or altered.** Fix: everything is
   POST, always, even reads.

## How data actually travels

```
JS object
  → JSON.stringify
  → base64 encode
  → FormData field "payload"
  → POST (no manual headers)
  → PHP: $_POST['payload']
  → base64_decode
  → json_decode
  → normal PHP array
```

## File map

```
assets/js/api-client.js     Frontend — ApiClient class, one per site
api/index.php                Front controller — every request lands here
api/config.php                Per-project settings (DB creds, debug flag)
api/core/Request.php          Decodes the incoming payload
api/core/Response.php         Standard {status, message, data} JSON output
api/core/Router.php           Maps "action" string -> endpoint handler
api/core/Csrf.php              Session-based CSRF issue/verify
api/core/Database.php         PDO singleton (SQLite or MySQL), prepared statements only
api/endpoints/ExampleEndpoint.php   Template for a feature — copy this file
data/                          Holds the SQLite file (random filename, see below)
```

## Spinning up a new project

1. Copy the whole folder into the new project's `htdocs/`.
2. Edit `api/config.php`: set `DB_DRIVER`, DB creds, `APP_DEBUG = false` before going live.
3. For each feature, copy `api/endpoints/ExampleEndpoint.php` to something
   like `Users.php`, rename the class, write your methods, and register it
   in `api/index.php`:
   ```php
   require_once __DIR__ . '/endpoints/Users.php';
   Users::register($router);
   ```
4. In your HTML, load the client and call it:
   ```html
   <script src="assets/js/api-client.js"></script>
   <script>
     const api = new ApiClient('/api');

     (async () => {
       await api.fetchCsrfToken(); // only needed if you're calling mutating endpoints

       const res = await api.post('saveContact', { email: 'supot@ka.com' });
       console.log(res.data);
     })();
   </script>
   ```

## Practical scenario: SSO-style login flow

This shows how CSS, the shared header/footer, and a custom login script all
wire together on top of the framework. "SSO" here means: log in once on
`login.php`, and every other page trusts the same PHP session — not
third-party OAuth (see note at the bottom for that case).

```
htdocs/
├── login.php              ← public page, shows login form
├── register.php           ← dev/test-only page to create an account
├── dashboard.php           ← protected page (session guard)
├── partials/
│   ├── header.php           ← <head>, links style.css, session-aware nav
│   └── footer.php           ← closes layout, loads scripts in order
├── assets/
│   ├── css/
│   │   └── style.css        ← ONE shared stylesheet, linked from header.php
│   └── js/
│       ├── api-client.js    ← framework's request bridge (unchanged)
│       ├── app.js           ← loaded on every page — creates the shared `api`
│       │                       instance, wires the logout link
│       ├── login.js         ← only loaded on login.php
│       └── register.js      ← only loaded on register.php
├── api/
│   ├── index.php
│   └── endpoints/
│       ├── ExampleEndpoint.php
│       └── Auth.php         ← login / register / logout / checkSession
```

**1. Where the CSS lives, and how the header wires it in**
Every stylesheet lives in one place: `assets/css/style.css`. `partials/header.php`
is the only file that links it (`<link rel="stylesheet" href="/assets/css/style.css">`),
so every page that includes that header automatically gets the same styling —
change the CSS once, every page updates.

**2. How a page is built**
```php
<?php
require $_SERVER['DOCUMENT_ROOT'] . '/bootstrap.php'; // same line, any depth
$pageTitle = 'Login';
require ROOT_PATH . '/partials/header.php';   // <head> + CSS + nav opens here
?>
  ...page markup...
<?php
$pageScript = 'login.js';                    // this page's own script
require ROOT_PATH . '/partials/footer.php';    // closes layout, loads scripts
```

See `EDITING-GUIDE.md` for how `bootstrap.php` makes relocating pages a
one-line change instead of a grep-and-replace across the project.

**3. Footer + custom scripts**
`footer.php` always loads scripts in the same order:
`api-client.js` (the framework) → `app.js` (shared behavior/global `api`
instance) → whatever `$pageScript` names (page-specific logic). `login.js`
and `register.js` don't create their own `ApiClient` — they reuse the one
`app.js` already made, so there's exactly one client instance per page load.

**4. The login flow itself**
- `login.php` renders the form → `login.js` calls `api.post('login', {...})`
- `api/endpoints/Auth.php::login()` verifies the password, then sets
  `$_SESSION['user_id']` / `$_SESSION['user_email']`
- `dashboard.php` checks `$_SESSION['user_id']` at the very top, *before*
  including `header.php` — an unauthenticated visitor gets redirected
  before any markup renders
- `header.php` itself reads the same session to decide whether the nav
  shows "Login" or the user's email + a Logout link
- Logout is wired once, globally, in `app.js` — it's not duplicated per page

**Note on real third-party SSO:** if a future project needs actual
Google/Facebook/Microsoft login instead of this local-account pattern,
swap `Auth.php`'s `login()` method for an OAuth callback handler — the
header/footer/session-guard structure around it stays exactly the same.



- **Every mutating endpoint calls `Csrf::requireValid($req->csrf())` first.**
  Read-only endpoints (like `getContacts`) can skip it.
- **Every query goes through `Database::query/queryOne/execute`** — all
  prepared statements, no string-concatenated SQL, ever.
- **One class per feature** in `api/endpoints/`, registered in `index.php`.
  Keeps a junior dev's changes isolated to one file.
- **`Response::success()` / `Response::error()`** are the only ways endpoints
  reply — the JS side always gets the same `{status, message, data}` shape,
  so `ApiClient` can handle errors generically across every project.
- Don't touch `api/core/*` per-project — if you need new shared behavior
  (e.g. rate limiting, logging), add it there once and it benefits every
  site built on this framework.

## Clean URLs (no .php in the address bar)

`.htaccess` at the **root** of `htdocs/` (not nested — that's the important
difference from `api/core/`'s reliability problem) rewrites `/login` to
`login.php` internally. Root-level `.htaccess` generally IS honored on
InfinityFree since `AllowOverride` is typically enabled at the docroot,
even when it's flaky a few folders deep.

All internal links/redirects in this scenario already use the clean form
(`/login`, `/dashboard`, `/register`) — both the clean URL and the old
`/login.php` will work simultaneously unless you uncomment the 301 redirect
block in `.htaccess`. Test the base rewrite works on your specific account
first before turning that on.

`api/` and `assets/` paths are untouched by this rule — it only matches
single-segment URLs with no slash, so `fetch('/api/index.php')` keeps
working exactly as before.

## Known InfinityFree gotchas this already handles

- **WAF blocking `Content-Type: application/json`** → solved via FormData + base64.
- **GET requests being blocked/altered** → solved by making everything POST.
- **Linux case-sensitivity on file paths** → keep filenames exactly matching
  `require_once` casing (this framework is consistent throughout).
- **`.htaccess` inside subfolders isn't reliably honored** → this framework
  does NOT depend on `.htaccess` for security anywhere. Instead:
  - Every file in `api/core/` and `api/endpoints/` starts with
    `defined('APP_BOOTSTRAP') or die(...)`. Only `index.php` defines that
    constant, so hitting `api/core/Database.php` directly in a browser just
    dies with a plain message instead of running.
  - The SQLite file gets a random 24-char filename (`db_a91f3c8e2b47.sqlite`)
    set in `config.php` — regenerate it per project with
    `php -r "echo bin2hex(random_bytes(12));"`. Obscurity, not access
    control, is the actual protection here since `.htaccess` "Deny all"
    can't be trusted in a nested folder on InfinityFree.
  - If your specific InfinityFree account *does* honor `.htaccess` (it
    varies by node), feel free to add `Require all denied` back in
    `data/` as a second layer — just don't rely on it alone.

## Not handled here (add if a project needs it)

- Rate limiting / brute-force protection on login-style endpoints.
- File uploads (this pattern is for JSON-shaped data; uploads need a
  separate `multipart` field, not the base64 payload trick).
- WebSocket-style real-time — InfinityFree doesn't support persistent
  connections; use polling (like your Rock Paper Scissors game does).
